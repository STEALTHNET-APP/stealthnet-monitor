# stealthnet-monitor

Панель мониторинга серверов и нод Remnawave. API и агент на Rust, интерфейс на React, PostgreSQL и HTTPS через Caddy.

**v0.1.3 — тестовая версия.** Есть рабочий сбор системных метрик, регистрация агентов, учёт аренды, правила оповещений и очередь Telegram. Экран демонстрации показывает будущий масштаб проекта; ограничения текущего сбора перечислены ниже.

## Установка

Выделенный сервер Debian 12 / Ubuntu 24.04, Docker Compose, домен с A-записью на сервер, свободные порты 80 и 443. Проверено на Linux x86_64. Для сборки рекомендуются 2 CPU и 4 ГБ RAM; тестовый запуск выполнялся на 1 CPU / 2 ГБ. Сборка на слабом сервере занимает несколько минут.

```bash
curl -fsSL https://raw.githubusercontent.com/STEALTHNET-APP/stealthnet-monitor/main/scripts/install-panel.sh -o install-stealthnet.sh && sudo bash install-stealthnet.sh --repo STEALTHNET-APP/stealthnet-monitor --domain monitor.example.com
```

Замените `monitor.example.com` своим доменом. Установщик скачивает последний опубликованный релиз, создаёт `/opt/stealthnet-monitor/.env` с индивидуальными секретами, собирает образы и запускает панель. На сервере, где уже занят 80/443, сначала настройте перенос существующего reverse proxy.

Пароль владельца — `ADMIN_PASSWORD` в `/opt/stealthnet-monitor/.env`. Логин не нужен. Файл доступен только владельцу; не публикуйте его. После установки панель открывает рабочий режим; демонстрацию можно включить кнопкой в верхней панели.

```bash
cd /opt/stealthnet-monitor
make start
make stop
make restart
make status
make logs
make backup
make update
make rollback
```

`make update` проверяет GitHub Releases, создаёт резервную копию, собирает релиз и проверяет запуск. При ошибке возвращает предыдущий образ приложения. `make rollback` вручную возвращает предыдущее приложение. Данные PostgreSQL хранятся в отдельном томе и не удаляются при `make stop`.

**Откат приложения не откатывает базу.** Для серии 0.1.x изменения схемы должны оставаться обратно совместимыми. Перед несовместимой миграцией нужен отдельный сценарий восстановления. Резервная копия содержит `database.dump`, `environment` и идентификатор образа; храните копию вне сервера. Проверка `pg_restore --list` входит в `make backup`; пробное восстановление описано в [DEPLOYMENT.md](DEPLOYMENT.md).

## Добавление ноды

1. «Добавить сервер»: выбрать существующую ноду или чистый сервер.
2. Указать название (в том числе на русском), IP (необязательно), регион, хостера и срок оплаты.
3. Для чистого сервера — `SECRET_KEY` и порт API ноды из Remnawave. Последняя стабильная версия `remnawave/node` подставляется из официального GitHub Releases автоматически и сохраняется с конкретным тегом. При необходимости образ можно изменить вручную; если GitHub недоступен, есть повторная попытка и ручной ввод.
4. Выполнить выданную команду от root. Токен действует 15 минут и используется один раз.
5. Агент появляется после первой телеметрии, обычно в течение 30 секунд.

Публичный IP сетевого интерфейса передаётся автоматически. При совпадении IP с нодой Remnawave её страна и число онлайн-пользователей попадают в карточку. Ноды Remnawave без агента тоже видны; системные метрики появятся после установки агента. Суммарный онлайн — сумма счётчиков нод, один пользователь может учитываться на нескольких нодах.

Агент устанавливается как systemd-служба `stealthnet-monitor-agent`. Сохраняет очередь метрик на 24 часа при потере связи. Повторная установка обновляет бинарный файл с сохранением регистрации. Пример обновления установленного агента:

```bash
curl -fsSL https://monitor.example.com/install-agent.sh -o /tmp/update-agent.sh
sudo bash /tmp/update-agent.sh --panel https://monitor.example.com
```

Панель отдаёт агент для архитектуры своей сборки. Смешанный парк x86_64/aarch64 требует размещения второго бинарного файла и его SHA-256 в каталоге downloads. Агент требует glibc совместимую с Debian 12 и systemd. Контейнерные ноды можно наблюдать с агента на хосте.

## Хостер, аренда и уведомления

В карточке сервера → **«Хостер и аренда»**:

- произвольное название провайдера;
- дата окончания оплаты — до 23:59:59 выбранного дня UTC;
- стоимость в месяц и валюта;
- фильтрация списка по хостеру, сортировка по окончанию аренды.

Правило **«Окончание аренды сервера»** отправляет Telegram за **7, 3, 1 день**, при истечении и продлении. Первый порог изменяется в оповещениях; этапы выше него пропускаются. Каждое напоминание отправляется один раз для данного срока. После изменения даты стадии пересчитываются. Удаление даты закрывает связанный инцидент без ложного уведомления о продлении. Дату владелец вносит вручную; интеграции с биллингом хостеров нет.

В **Настройки → Telegram** сохраните токен своего бота, привяжите личный чат одноразовой `/start`-командой или укажите ID группы, выберите события и отправьте тест. Бот должен иметь доступ к указанному чату. Если у бота уже настроен webhook, автоматическая привязка не меняет его: используйте отдельного бота либо явный chat ID.

Поддерживаются: потеря связи, CPU, RAM, диск, трафик, новые признаки BitTorrent, аренда и восстановление. Правила имеют порог, длительность, повтор, важность и область применения. Очередь проверяется отдельным процессом каждые 3 секунды и не ждёт синхронизации Remnawave. Пользователи Remnawave сохраняются транзакциями по странице, чтобы большие импорты не создавали отдельную запись на диск для каждой учётной записи. Очередь сохраняется в БД, соблюдает Telegram `retry_after`, после восьми неудачных попыток помечает сообщение ошибкой. «Доставлено» означает успешный ответ Telegram API, а не прочтение. При аварии между отправкой и фиксацией результата возможен повтор сообщения.

Токены Remnawave и Telegram зашифрованы AES-256-GCM ключом `ENCRYPTION_KEY`. API возвращает маску токена; секреты не попадают в историю доставки. При восстановлении базы сохраните исходный `ENCRYPTION_KEY`.

## Доступ к Remnawave

Интеграция работает только на чтение: `GET /api/nodes`, `GET /api/users` и `GET /api/hwid/devices`. Она не отправляет запросы на создание, изменение, блокировку или удаление клиентов. После полной синхронизации очищаются только устаревшие копии пользователей в собственной базе мониторинга. Если загрузка страницы не удалась, очистка не выполняется. Это проверяется интеграционным тестом с записью всех запросов к тестовому API.

Сценарий «Чистый сервер» отдельно устанавливает контейнер Remnawave Node на сервер, где вы запускаете команду. Существующую ноду подключайте сценарием «Работающая нода».

### Журнал подключений Xray

Если на сервере найден ровно один работающий официальный контейнер `remnawave/node`, установщик подключает службу `stealthnet-monitor-xray`. Она читает существующий `/var/log/xray/current` через `/proc`, определяет контейнер через `docker inspect`, а активную конфигурацию Xray — через локальный Unix-сокет (GET) или JSON-файл старых сборок. Контейнер VPN не перезапускается, конфигурация и клиенты Remnawave не изменяются. При недоступном журнале сборщик повторяет чтение; автоматически включать логирование он не будет.

С v0.1.3 сборщик сопоставляет IP и исходный порт журнала с `ss -tine`: TCP-каналы получают наблюдаемую длительность, входящие/исходящие байты и RTT. Отсчёт начинается при первом наблюдении, прежний трафик не приписывается новому сеансу. Идентификатор сокета различает повторное использование одного порта. Эти байты относятся к внешнему TCP-каналу VPN, включая его служебный обмен, а не к каждому запросу внутри туннеля. Если один сокет сопоставлен нескольким аккаунтам, его трафик не распределяется произвольно. UDP внутри TCP-туннеля может быть виден в журнале; нативные UDP-сокеты не получают TCP-счётчики. При отсутствии счётчиков остаётся наблюдение журнала с объяснением недоступности.

BitTorrent определяется по срабатываниям **существующего** правила `protocol: ["bittorrent"]`: нужен включённый sniffing и отдельный outbound, не используемый другими типами правил. События объединяются по пользователю/IP в пятиминутные окна. Нулевой результат не доказывает отсутствие всего BitTorrent. Содержимое трафика, адреса назначения и секреты активной конфигурации не сохраняются и не отправляются панели.

Сборщик работает как root, сетевой агент — как отдельный пользователь; обмен через каталог с ограниченными правами. За 15 секунд передаётся до 1000 наблюдений, очередь и активные сеансы ограничены 20 000 записями, журнал обмена — 10 МБ. Служба ограничена 5% CPU и 192 МБ памяти. Для нескольких контейнеров или другого пути нужен отдельный источник `--events`.

Синхронизация нод выполняется отдельно каждые 30 секунд, пользователей и HWID — каждые 5 минут. Поддерживаются обёртка `response`, массивы и именованные списки, вложенный `userTraffic` и старые плоские поля. Полный импорт постраничный, до 1 млн записей каждого типа; повторённые/некорректные страницы прерывают импорт без удаления неимпортированных сохранённых записей. Ошибка необязательного HWID API отображается отдельно. Чтение Remnawave использует только GET.

Поиск пользователей, устройств, соединений и обнаружений выполняется по всей базе панели с серверной пагинацией. Имя пользователя, UUID и числовой ID связываются одинаково в поиске, списках и профиле. Устройства связываются с подключениями через аккаунт; точное соответствие HWID конкретному VPN-каналу не утверждается. История онлайна нод сохраняется с момента обновления, график пользователя строится по истории именно его счётчика Remnawave. Итоги сетевого трафика суммируют измеренные интервалы агентов; неизвестные пропуски не заполняются.

### География подключений

Панель автоматически скачивает **DB-IP City Lite** и **DB-IP ASN Lite** и определяет страну, город и примерные координаты IP локально. IP пользователей не отправляются внешнему API. Первая загрузка занимает некоторое время (около 60 МБ в архиве / 125 МБ на диске); до её завершения интерфейс показывает состояние загрузки. База хранится в постоянном Docker-томе `geoip_data`, проверка нового месячного выпуска идёт раз в 6 часов. При первом сбое загрузка повторяется через минуту; уже загруженная база сохраняется при ошибке обновления. Для запуска без Compose каталог задаётся через `GEOIP_DIR`.

На вкладке **Карта → Подключения** отображаются реальные наблюдения выбранной ноды и периода: группы IP, линии к ноде и список пользователей по нажатию. Масштаб разделяет близкие группы; режим «Весь мир» показывает географию за пределами Европы. В карточке «Откуда подключаются» показываются города и число наблюдаемых IP. Неизвестные/частные IP не получают выдуманных координат.

Карта использует последние 1000 записей snapshot, отфильтрованные по времени последней активности. Это выборка наблюдений, не полная история сессий и не число подключённых сейчас людей. Один пользователь может иметь несколько IP, а TCP/UDP одного IP не увеличивают счётчик IP. Имя учётной записи сопоставляется со всей сохранённой базой пользователей, иначе остаётся ID из журнала. Геолокация приблизительная, особенно у мобильных операторов, VPN и прокси.

Источник: [IP Geolocation by DB-IP](https://db-ip.com), базы [DB-IP City Lite](https://db-ip.com/db/download/ip-to-city-lite) и [ASN Lite](https://db-ip.com/db/download/ip-to-asn-lite), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). Ссылка на источник также присутствует на страницах панели. База скачивается отдельно и не включается в Git.

## Ограничения первой версии

- Без Remnawave API и журналов реальные пользователи, устройства и подключения остаются неизвестными. Неизвестное значение отображается как `—`.
- ОС/модель устройства берётся из HWID, если источник их передаёт; агент на сервере не может достоверно определить все устройства за зашифрованным туннелем.
- Универсальный DPI не реализован. «Торренты» показывает подтверждённые срабатывания настроенного Xray, а не все зашифрованные/обфусцированные BitTorrent-потоки.
- На карте показываются вручную выбранные регионы и приблизительные положения стран из Remnawave. Автоматическая карта стран сейчас покрывает 21 страну; неизвестная география не заменяется случайной координатой. География подключений строится по наблюдаемым IP из Xray и локальной базе DB-IP City Lite. Неуказанный регион не получает выдуманный маркер.
- Поиск и профили используют полную базу. Обзорный snapshot и карта ограничены 1000 последними подключениями, 5000 пользователями/устройствами и 2000 системными отсчётами за сутки. История онлайна агрегируется по 5 минутам за 7 дней; более ранние данные не восстанавливаются задним числом. Итоги трафика рассчитываются отдельно по сохранённым интервалам. Нагрузочные пределы необходимо проверять на конкретном парке.
- Нагрузка сотен реальных агентов не проверялась. Один владелец, без RBAC, нескольких проектов и высокой доступности.
- Демо имеет отдельные синтетические данные и не отправляет Telegram. Для отправки нужен рабочий режим и реальный токен.

Структурированный журнал подключается параметром установщика `--events /path/events.jsonl`; служба должна иметь права чтения файла. Одна JSON-запись на строку:

```json
{"id":"unique-event-id","time":1789488000000,"kind":"detection","user":"account-reference","ip":"192.0.2.10","evidence":"BitTorrent protocol matched by the configured upstream source"}
```

`time` — реальное время события в миллисекундах Unix, `kind` — `connection` или `detection`. Идентификатор стабилен при повторном чтении. Сбор содержимого пользовательских сообщений агент не выполняет.

## Разработка

Rust 1.94, Node.js 22.18+ (тесты TypeScript используют встроенное удаление типов), npm.

```bash
npm --prefix web ci
# Задайте свой пароль минимум 12 символов:
export ADMIN_PASSWORD='local-development-only-change-me'
make dev-api
# В другом терминале:
make dev-web
make test
```

API: `127.0.0.1:8787`, Vite: `127.0.0.1:5178`. Без DATABASE_URL локальная разработка использует SQLite в `.runtime/data`. `/api/health` общедоступен; данные и настройки требуют сессии владельца. Агент использует отдельный credential, который хранится в БД только в виде SHA-256.
