# stealthnet-monitor

Панель мониторинга серверов и нод Remnawave. API и агент на Rust, интерфейс на React, PostgreSQL и HTTPS через Caddy.

**v0.1.0 — первая тестовая версия.** Есть рабочий сбор системных метрик, регистрация агентов, учёт аренды, правила оповещений и очередь Telegram. Экран демонстрации показывает будущий масштаб проекта; ограничения текущего сбора перечислены ниже.

## Установка

Выделенный сервер Debian 12 / Ubuntu 24.04, Docker Compose, домен с A-записью на сервер, свободные порты 80 и 443. Проверено на Linux x86_64. Для сборки рекомендуются 2 CPU и 4 ГБ RAM; тестовый запуск выполнялся на 1 CPU / 2 ГБ. Сборка на слабом сервере занимает несколько минут.

```bash
curl -fsSL https://raw.githubusercontent.com/STEALTHNET-APP/stealthnet-monitor/main/scripts/install-panel.sh -o install-stealthnet.sh && sudo bash install-stealthnet.sh --repo STEALTHNET-APP/stealthnet-monitor --domain monitor.example.com
```

Замените `monitor.example.com` своим доменом. Установщик скачивает последний опубликованный релиз, создаёт `/opt/stealthnet-monitor/.env` с индивидуальными секретами, собирает образы и запускает панель. На сервере, где уже занят 80/443, сначала настройте перенос существующего reverse proxy.

Пароль владельца — `ADMIN_PASSWORD` в `/opt/stealthnet-monitor/.env`. Логин не нужен. Файл доступен только владельцу; не публикуйте его. После установки панель открывает рабочий режим; демонстрацию можно включить кнопкой в верхней панели.

```bash
cd /opt/stealthnet-monitor
make start
make stop
make restart
make status
make logs
make backup
make update
make rollback
```

`make update` проверяет GitHub Releases, создаёт резервную копию, собирает релиз и проверяет запуск. При ошибке возвращает предыдущий образ приложения. `make rollback` вручную возвращает предыдущее приложение. Данные PostgreSQL хранятся в отдельном томе и не удаляются при `make stop`.

**Откат приложения не откатывает базу.** Для серии 0.1.x изменения схемы должны оставаться обратно совместимыми. Перед несовместимой миграцией нужен отдельный сценарий восстановления. Резервная копия содержит `database.dump`, `environment` и идентификатор образа; храните копию вне сервера. Проверка `pg_restore --list` входит в `make backup`; пробное восстановление описано в [DEPLOYMENT.md](DEPLOYMENT.md).

## Добавление ноды

1. «Добавить сервер»: выбрать существующую ноду или чистый сервер.
2. Указать название, IP (необязательно), регион, хостера и срок оплаты.
3. Для чистого сервера — `SECRET_KEY` из Remnawave, фиксированную версию `remnawave/node` и порт API ноды.
4. Выполнить выданную команду от root. Токен действует 15 минут и используется один раз.
5. Агент появляется после первой телеметрии, обычно в течение 30 секунд.

Агент устанавливается как systemd-служба `stealthnet-monitor-agent`. Сохраняет очередь метрик на 24 часа при потере связи. Повторная установка обновляет бинарный файл с сохранением регистрации. Пример обновления установленного агента:

```bash
curl -fsSL https://monitor.example.com/install-agent.sh -o /tmp/update-agent.sh
sudo bash /tmp/update-agent.sh --panel https://monitor.example.com
```

Панель отдаёт агент для архитектуры своей сборки. Смешанный парк x86_64/aarch64 требует размещения второго бинарного файла и его SHA-256 в каталоге downloads. Агент требует glibc совместимую с Debian 12 и systemd. Контейнерные ноды можно наблюдать с агента на хосте.

## Хостер, аренда и уведомления

В карточке сервера → **«Хостер и аренда»**:

- произвольное название провайдера;
- дата окончания оплаты — до 23:59:59 выбранного дня UTC;
- стоимость в месяц и валюта;
- фильтрация списка по хостеру, сортировка по окончанию аренды.

Правило **«Окончание аренды сервера»** отправляет Telegram за **7, 3, 1 день**, при истечении и продлении. Первый порог изменяется в оповещениях; этапы выше него пропускаются. Каждое напоминание отправляется один раз для данного срока. После изменения даты стадии пересчитываются. Удаление даты закрывает связанный инцидент без ложного уведомления о продлении. Дату владелец вносит вручную; интеграции с биллингом хостеров нет.

В **Настройки → Telegram** сохраните токен своего бота, привяжите личный чат одноразовой `/start`-командой или укажите ID группы, выберите события и отправьте тест. Бот должен иметь доступ к указанному чату. Если у бота уже настроен webhook, автоматическая привязка не меняет его: используйте отдельного бота либо явный chat ID.

Поддерживаются: потеря связи, CPU, RAM, диск, трафик, новые признаки BitTorrent, внешние жалобы, аренда и восстановление. Правила имеют порог, длительность, повтор, важность и область применения. Очередь сохраняется в БД, соблюдает Telegram `retry_after`, после восьми неудачных попыток помечает сообщение ошибкой. «Доставлено» означает успешный ответ Telegram API, а не прочтение. При аварии между отправкой и фиксацией результата возможен повтор сообщения.

Токены Remnawave и Telegram зашифрованы AES-256-GCM ключом `ENCRYPTION_KEY`. API возвращает маску токена; секреты не попадают в историю доставки. При восстановлении базы сохраните исходный `ENCRYPTION_KEY`.

## Что собирается сейчас

| Источник | Данные |
| --- | --- |
| Агент | CPU, RAM, заполнение наиболее занятого диска, входящая/исходящая скорость интерфейсов, время последнего отчёта, версия |
| Remnawave API | Учётные записи и их трафик, доступные HWID-устройства, сведения о логических нодах |
| Структурированный журнал агента | Наблюдаемые соединения и признаки BitTorrent с доказательством события |
| Владелец панели | Аренда, хостер, стоимость, внешние жалобы, настройки и правила |

### Ограничения первой версии

- Без Remnawave API и журналов реальные пользователи, устройства и подключения остаются неизвестными. Неизвестное значение отображается как `—`.
- ОС/модель устройства берётся из HWID, если источник их передаёт; агент на сервере не может достоверно определить все устройства за зашифрованным туннелем.
- Автоматический разбор Xray access-log, DPI, база GeoIP и сопоставление аккаунт ↔ соединение ещё не реализованы. Пункт «Торренты» принимает сигналы структурированного журнала; это не доказательство нарушения и не обнаружение всего зашифрованного BitTorrent.
- На карте показываются вручную выбранные регионы серверов. В рабочем режиме география клиентских подключений отсутствует до подключения соответствующего источника. Неуказанный регион не получает выдуманный маркер.
- Синхронизация пользователей постраничная до 100 000 записей. HWID пока загружаются первой страницей (500). Snapshot UI ограничен 5000 пользователями/устройствами, 1000 событиями каждого типа и 2000 последними отсчётами за сутки. График отображает доступные отсчёты выбранного периода; историческая агрегация для большого парка и серверная пагинация интерфейса требуют следующего этапа.
- Нагрузка сотен реальных агентов не проверялась. Один владелец, без RBAC, нескольких проектов и высокой доступности.
- Демо имеет отдельные синтетические данные и не отправляет Telegram. Для отправки нужен рабочий режим и реальный токен.

Структурированный журнал подключается параметром установщика `--events /path/events.jsonl`; служба должна иметь права чтения файла. Одна JSON-запись на строку:

```json
{"id":"unique-event-id","time":1789488000000,"kind":"detection","user":"account-reference","ip":"192.0.2.10","evidence":"BitTorrent protocol matched by the configured upstream source"}
```

`time` — реальное время события в миллисекундах Unix, `kind` — `connection` или `detection`. Идентификатор стабилен при повторном чтении. Сбор содержимого пользовательских сообщений агент не выполняет.

## Разработка

Rust 1.94, Node.js 22.18+ (тесты TypeScript используют встроенное удаление типов), npm.

```bash
npm --prefix web ci
# Задайте свой пароль минимум 12 символов:
export ADMIN_PASSWORD='local-development-only-change-me'
make dev-api
# В другом терминале:
make dev-web
make test
```

API: `127.0.0.1:8787`, Vite: `127.0.0.1:5178`. Без DATABASE_URL локальная разработка использует SQLite в `.runtime/data`. `/api/health` общедоступен; данные и настройки требуют сессии владельца. Агент использует отдельный credential, который хранится в БД только в виде SHA-256.
